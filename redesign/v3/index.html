ShareTrip · Hotel search

Speeding up hotel search

Problem
Search processed hotel IDs in chunks, one after another, so later chunks waited for earlier ones.
The tempting answer
Run the calls inside each chunk concurrently, and keep the loop. A loop that awaits each complete chunk still makes the later chunks wait.
What we did
The search returns a session at once and fills it in the background. Chunks run concurrently within a bound, smaller early chunks bring first results sooner, and shared counts update atomically.
Result
First results appear while the rest of the search continues.

ShareTrip · Bookings

Making booking retries safe

Problem
A booking request can arrive more than once, after a timeout or a repeated tap. A repeat must not take a second room.
The tempting answer
Check whether the booking exists, then create it. Two requests can both finish the check before either one creates the booking.
What we did
We use the booking identifier to recognise repeats. A MySQL named lock orders work on the same booking, and a transaction groups the database changes. Cancellation follows the same rules.
Result
A repeated request returns the existing booking, and inventory changes once.

ShareTrip · Public gateway

Rate limits that follow the caller

Problem
A public gateway must slow down abusive callers without slowing down everyone else. Many normal users can share one address, and a proxy can hide the real one.
The tempting answer
One shared limit for the whole platform. It is simple, but one busy caller then uses up the allowance of every other caller.
What we did
Each caller gets its own bucket. The caller's address comes only from the forwarded header that the platform's own ingress sets. One wide platform limit stays as a last safety net.
Result
A busy caller now uses up only its own allowance. Every other caller keeps its normal speed.

PadelHub BD · Sole developer

A ranking that players can check

A ranking and tournament platform for padel players in Bangladesh. Players submit match results from their phones at the court. An opponent or an admin confirms each result, and confirmed results feed a public ranking. I built it end to end, with Laravel, Filament and MySQL.

Problem
A ranking only works if players trust it. One hidden rule, and they stop submitting results.
The tempting answer
Keep the formula in code and show only the final number. Players cannot check a number they cannot trace, and every rule change becomes a deploy.
What I did
The platform has four parts: the ranking engine, the tournament engine, the admin panel and the public site. I put every ranking constant in one config file, and the tests read that same file. Each player has a breakdown page that shows which results produced the points. The public table is served from precomputed snapshots. Tie-breaks follow one fixed ladder.
